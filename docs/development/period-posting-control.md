# Reviewed period posting control

NIN-17 adds canonical PeriodControl to the shared ontology. Each company/ledger/book/period tuple has one stable identity and exact references to its company, ledger, book, period, chart, currency and calendar. A control declares OPEN or LOCKED with a reason through the existing independent ResourceProposal review. This is permission to attempt guarded canonical journal publication, not certified close completion, accounting consumption authority or ERP execution.

No control is implicitly open. Missing, hidden, withdrawn, stale or mismatched control state prevents new JournalEntry and JournalLine publication. Existing journal readback remains available. Reopening is another reviewed version with an explicit reason and expected prior version. Every request pins the seven accounting versions; a late context correction refuses promotion. Control and journal changes cannot share a proposal, nor can a control proposal simultaneously change its underlying accounting context.

The publication service and PostgreSQL enforce the current OPEN control under the existing canonical transaction lock. Journals retain the exact PERIOD_POSTING_CONTROL dependency. The database checks the actual current head and its coherent accounting references, including the binding's ledger/book/period/currency and source scope's company/chart. It serializes after acquiring the lock and reads server time there, avoiding a stale statement-start timestamp after waiting. Backdated journal effective dates cannot bypass the current posting lock. Controls cannot be future scheduled or have an expiry that silently reopens a period. Recorded lifecycle withdrawal or unavailability prevents further use.

Migration 052 adds the posting guard and one-control identity constraint. Migration 053 makes the existing effective-version helper explicitly resolve its table under a restricted SQL search path; its ordering, bitemporal predicate and caller RLS remain unchanged. The first native control test exposed that integration defect, which was fixed before this capability was committed.

Companies → Accounting displays the current control beside historical journals after a validated accounting selection. State changes require an explicit selection and reason. Submission retains its exact request for uncertain retries, rejects mismatched response identities, and opens the existing Workflows & Actions review. A received receipt can be followed by an explicit new change after refreshing state. The business review names the requested state and reason; exact identities remain available for inspection. No control panel mounts for an unconfigured company.

The API uses GET `/v1/ontology/period-control` and POST `/v1/ontology/period-control/proposal`. Creation/retry returns the same retained proposal identity; changing request content under that identity conflicts. Present-state responses are advisory, always declaring `current_use_authorized=false`, `financial_close_certified=false` and `erp_posted=false`.

Verification and limits are recorded in `evidence/nin17-period-posting-control.json`. Ten focused checks passed, including two native database cases. Live web-proxy reads and the browser selected the same isolated synthetic company/ledger/book/period, showed LOCKED, and inspected its two-line balanced historical journal with accounting-input ineligibility still explicit. No browser posting-control proposal was submitted. The browser check also exposed a journal-footer label overflowing its amount column; the label now wraps within its cell. Synthetic tests exercise control review and database enforcement separately from authentic source publication. Real SGP remains without accepted financial configuration. This capability does not close the full NIN-17 or NIN-25 acceptance contract.
